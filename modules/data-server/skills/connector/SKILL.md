# connector

本技能让你访问企业管理员已经接入平台的外部系统。**平台只提供能力和护栏，不替你决定怎么查——查询语句是你自己写的。**

## 使用顺序

**不要跳步，也不要凭空猜表名。**

1. `conn_list` — 先看有哪些连接器可用、各自有什么能力、健不健康
2. `conn_catalog` — 看某个连接器里有哪些表 / 对象（只给名字和注释，很便宜）
3. `conn_describe` — 看某张表的字段、类型、注释
4. `conn_query` — 写查询语句执行；或 `conn_invoke` — 调接口
5. `conn_execute` — **只有在真的要改数据时**才走到这一步，而且必须先用第 4 步查清楚会影响哪些行（见下面「写操作」）

> **第 2 步常常可以跳过。** 如果上下文里已经给了**「已接入数据源的表清单」**，那就是
> `conn_catalog` 的缓存版本，你可以直接从里面挑表、进第 3 步——这正是它被提前给你的原因。
>
> **但以下三种情况必须老老实实调 `conn_catalog`**：
> ① 清单里找不到你要的表；② 清单自己说了只列出了一部分（它会写明列了几张、共几张）；
> ③ 你怀疑结构变过——它是快照，不是实时的。
>
> **在调过 `conn_catalog` 之前，永远不要因为清单里没有就断言「系统里没有这张表」。**
> 清单是按**有没有注释 / 有没有语义**排的（都没有的排在后面，同档按表名），预算不够时砍掉的
> 就是末尾那些。所以被砍掉的恰恰是**平台对它一无所知**的表——不是小表，也不是不重要的表。
> 「不在清单里」完全不等于「不存在」，反而正是最容易漏掉的那一类。

> **第 2、3 步的返回里出现 `empty_table: true`，就别再往这张表上写查询了**——
> 平台探过，它一行数据都没有。详见下面「`empty_table`：这一次，零结果就是『没有』」。

还有一个不在这条链上的工具：`conn_define_metric`。它**不碰客户系统**，只在用户澄清了一条业务口径之后把那条口径记进平台自己的说明书，见下面「最大的风险」。

前三步都很便宜，第四步才会真的打到客户的生产系统上，第五步会**改动**那个系统。**宁可多花两轮确认表结构，也不要写一条基于猜测的查询。**

## `semantic` 和 `comment` 不是一回事

客户给的是一个只读账号，库里常常是 `t_ord_mst` / `t_ord_dtl` 这样的表名。平台会为每条连接维护一份「说明书」，它随 `conn_catalog` / `conn_describe` 的返回一起给你：

| 字段 | 谁说的 | 怎么用 |
|---|---|---|
| `comment` | **客户自己**写在库里的注释 | 一手事实，优先采信 |
| `semantic` | **平台**维护的业务说明 | 二手理解，可能过时、也可能推错 |

**两者并排给出，永远不会被合并成一个字段**——合并之后你就分不清这句话是谁说的，而「谁说的」正是它该不该被采信的唯一判据。两者冲突时以 `comment` 为准，并在回答里说明这个冲突。

`conn_catalog` 条目上的 `semantic` 是截短的一句，够选表用。**这张表的完整说明在 `conn_describe` 返回的顶层 `semantic`**，同样和顶层的 `comment` 并排。

表级的 `semantic_status: STALE`，以及 `semantic_note`（`conn_describe` 的顶层或字段上），表示所挂的结构已经变过了，那句说明可能已经不成立，**以本次返回的 `type` / `comment` 为准**。

说明书里**不会**出现枚举值的含义。看到 `status tinyint` 取值 0/1/2/3，说明书只会告诉你这是个状态码、含义待确认，不会告诉你 0 是「待支付」——那句话完全合理、完全可能错，而且没有任何办法能发现它错。**你也不要自己补上这一句**，该问就问。

（平台有可能把这一列**实际存在的那组取值**查出来给你，见下面「枚举值」那一节。给的是取值本身，永远不会是它们的含义。）

## ★ 最大的风险：能跑通的查询，不等于口径对的查询

这是本技能里最需要你警惕的事，比语法错误严重得多。

一条 SQL 可以**完全合法、顺利执行、返回一个看起来合理的数字，而口径是错的**。它不会报错，数量级也像那么回事，只有懂业务的人盯着才会发现。典型的歧义：

- 「上个月」含不含本月 1 号？按哪个时区算？
- 「客户」指下单人还是付款方？
- 「销售额」要不要减去退款？含不含税？含不含运费？
- 要不要去重？按订单去重还是按用户去重？

**遇到这类歧义，问用户，不要自己假定。** 一句「这里的销售额是否需要扣除退款？」比一个错误的数字有价值得多。

### 用户答完之后，把口径记下来

口径**根本不在客户的数据库里**——它在一份财务口径文档里，或者在某个人的脑子里。所以它只能靠问。但光问不够：不记下来，下一轮对话你还会再问一遍同一句话，而且两次拿到的答案不保证一致。

得到明确答复之后，**立刻调用 `conn_define_metric`** 把它写进这条连接的说明书：

```
conn_define_metric(connector="crm", term="销售额", definition="按支付时间统计，扣除退款，不含运费")
```

- **只记用户明确回答过的。** 你自己推测的口径没有任何依据，写进去比不写危险得多——它会被后面每一轮对话当成已确认的事实。
- 用户语气不确定（「大概是扣了吧」）**不算确认**，继续问清楚再记。问过之后他确实说不清，见下一节。
- 用户纠正口径时，用**同一个 `term`** 再调一次覆盖它，不要新造一个近义词条（「销售额」和「销售金额」会变成两条各说各话的口径）。

### 用户自己也说不清：两个数都算，一个都不记

先问，这条不变；「大概吧」也还是不算确认。但问过之后用户**确实答不上来**（「我也不清楚财务怎么算」「你看着办」），就**不要逼他选，也不要替他选**。两种口径都算出来，把两个数和各自按什么算的并排摆出来：

> 上个月销售额：扣退款是 ¥120 万，不扣是 ¥135 万。（两条查询语句和命中行数附后）该用哪个，需要跟懂口径的人确认。

两条查询照样要亮出过程。数字摆在一起，真正懂的人一眼就能看出该用哪个；逼一个不确定的人二选一，得到的只是一个看起来确认过的猜测。

**这种情况绝对不要调 `conn_define_metric`**——没有人确认过任何一种。一条口径一旦记下，之后所有人问到这个词都会被悄悄按它算，而且这件事**不会有任何提示**。记错了要清掉，得由企业超管到管理台去删那一行，问数的人自己做不到。两个数恰好一样也不记：这个月没有退款，不代表口径定了。

### 引用存过的口径时，必须亮出依据

`conn_catalog` 的返回里会带 `glossary`（已经被人确认过的口径）和 `ambiguities`（平台看得出有歧义、但还没有人回答的地方）。

`glossary` **要在选表之前就读**：销售额扣不扣退款，决定了你要不要 join 退款表——等选完表再看到它，那个决策点已经过去了。`ambiguities` 里的问题，碰到就问用户，不要自己填一个听起来合理的答案。

用到 `glossary` 里的口径时，答案里要把 `basis` 带出来：

> 上个月销售额 ¥120 万。（口径：扣除退款，9月13日由张三确认）

**为什么这半句不能省**：任何能对话的人都能覆盖口径，而覆盖是**无声**的——被改之后，下一轮问到这个词，你只会给出一个按新口径算出来的、看着完全正常的数字。回答里亮出的这半句，是懂业务的人在日常使用中**看得见**「这条口径不对」的地方。省掉它，一个错口径可以错上几个月都没人知道。

**用户说某条口径记错了，怎么办**：平台有纠正入口——管理台的语义层页面可以删掉记错的那一行——但它**只对企业超管开放**，问数的业务方点不到。所以在**用户明确指出某条已记下的口径不对**时（「不对，销售额不该扣退款」「这条是谁加的，去掉」），告诉他需要找企业超管去管理台删掉，并把 `term` 和你看到的那条口径原文一起报给他，方便他定位。如果用户本人就能改，那是另一条路：让他用同一个 `term` 重新答一次，你调 `conn_define_metric` 覆盖（覆盖会留痕）。

**这条只在上面那种情况下说。** 用户只是问数、或者只是在回答你的口径问题，就不要提管理台、也不要提企业超管——那时这句话是噪声，而且会让人以为有什么东西坏了。

### 平台附在上下文里的口径说明是强制的

口径会**经两条路**到你面前，不要以为只有一条：

1. **概览里的全量**——每轮请求，平台会把已授权连接器的表清单连同**已确认的口径**一起放进 system 上下文。也就是说，很多时候你不调 `conn_catalog` 就已经看得到口径了。（这条路可以被 `connector.overview.enabled=false` 关掉，关掉时你就只剩下面第 2 条。）
2. **本轮的逐字命中**——用户这一轮的话里逐字命中了已确认的词条时，平台会把那几条定义连同依据**再**附一次。这条路是正确性机制，不随概览开关关闭。

下面这几条说的是第 2 条路的那段文字。它不是检索出来的相关内容，也不是建议：

- 命中判断是平台用确定性规则做的，**不要自己再判一次相不相关**，也不要用你的常识去覆盖它；
- 本轮凡涉及这些词，一律按它给的口径写查询，答案里把依据原样带上；
- 它是**附加**在用户原话旁边的说明，**用户那句话一个字都没有被改过**——不要试图去「还原」用户的原意；
- 它只对**本轮**这句话生效，而且只属于它点名的那条连接；别的数据源不适用。

段落里如果说还有命中但没展开的词条，那几条就去 `conn_catalog` 的 `glossary` 里取。

### 关联（`joins`）：先看 `verified`，它决定你接下来该做什么

`conn_describe` 返回的 `joins` 是平台维护的、**可以按单列直接连**的表关系。每条都带 `verified` 和 `basis`——前者是验到什么程度，后者是一句人话说清依据（验过的会把采了多少、命中多少一并写出来）。

**`joins` 里的 `verified` 只有三个取值，对应三种不同的动作，不要当成一回事：**

| `verified` | 它的意思 | 你该做什么 |
|---|---|---|
| `CONFIRMED` | 真的去采过数据，两边对得上 | 直接用。**不必**再为它跑一次 COUNT 自验——那只是白花客户库的资源 |
| `UNDECIDABLE` | 采过数据，但**判不出来**（表几乎是空的、探查没跑完…），`basis` 里写着具体原因 | 这**不等于**关系不成立。依赖它之前自己跑一条 COUNT 核一次；核不出来就如实说 |
| `NONE` | **压根没采过数据**，是从列名和注释推出来的 | 名字长得像不等于真的能连上。用之前必须先跑 COUNT 自验 |

**`UNDECIDABLE` 和 `NONE` 是两回事**：前者已经花过一次探查、结论是判不出来（再探一次多半还是判不出来，要核就自己核）；后者根本没人去看过。

采样只有一部分对得上的关系（`WEAK`）**不在 `joins` 里**，它和多态外键、复合键一起放在 `unreliable_relations`，见下一节。平台采过数据、发现**不成立**的关系（`REJECTED`）两处都不会出现。所以这份清单是筛过的——但「没出现」也可能只是没推导到，不代表两张表之间没有关系。

自验就是一条便宜的 `COUNT`：

```sql
SELECT COUNT(*) FROM t_ord_dtl d JOIN t_ord_mst m ON d.order_id = m.id;
-- 与 SELECT COUNT(*) FROM t_ord_dtl 对一下：差很多就说明这条关系不成立
```

对不上就别硬用，如实告诉用户这条关联不可靠。带 `stale_note` 的关系表示两端的列已经变过，**无论 `verified` 是什么都不能直接采信**——先看一眼现在的结构。

引用这类关系得出的结论时也要说明，例如「（该结论依赖 t_ord_dtl.order_id → t_ord_mst.id 这条关联，已用 COUNT 核对过）」。

### ★ 不可靠的关联（`unreliable_relations`）：单列 join 连出来的是错的行，不是少的行

`conn_describe` 可能另外返回 `unreliable_relations`，里面是**不能按单列直接连**的关系：

- 采样只有一部分对得上的（`verified: WEAK`）；
- 所有**多态外键**（`join_kind: POLYMORPHIC`）：同一列按另一列的类型，指向不同的表。比如评论表的 `resource_id`，`resource_type` 是订单时指订单表，是商品时指商品表；
- 所有**复合键**（`join_kind: COMPOSITE`）：对面那一列只是一个多列唯一键的一部分，单独没有唯一约束。

后两种**不管 `verified` 多好看**都放在这里。包含率只能说明「这个 id 在对面存在」，说明不了「连上的是不是那一行」：一条商品评论的 `resource_id` 恰好等于某个订单 id，按单列 join 它就成了那个订单的评论。**SQL 不报错，数量级正常，数是错的。** 采样只对上一部分的关系，最常见的原因恰恰就是这两种。

更麻烦的是，上一节那条 `COUNT` 自验**核不出这种错**——错连上的行照样被计数。对这一节的关系，光跑 COUNT 不算验证过。（复合键 `condition` 里让你比对面 `COUNT(*)` 和 `COUNT(DISTINCT to_column)`，那是另一回事：它查的是对面那一列实际是不是一行一个，不是拿 join 前后的行数对账。）

每条都带 `care_reason`（为什么要小心）和 `condition`（要用它必须满足什么）。**照 `condition` 做，满足不了就不用：**

| 情况 | 你必须做的 |
|---|---|
| `join_kind: POLYMORPHIC` | join 时同时过滤判别列 `discriminator_column`。有 `discriminator_value` 就照它写；没有，要么是平台没记下哪个取值对应目标表，要么是这条连接当前没开放样本值、取值不提供给你（`condition` 里会说是哪种）。两种做法一样：先查这一列有哪些取值，**哪个取值对应目标表拿不准就问用户**，不要按名字猜。对面如果同时是复合键，`condition` 会把复合键那一段一并写出——两段都要照做 |
| `join_kind: COMPOSITE` | `composite_columns` 是**对面那张表**的完整唯一键（写的是对面的列名），**不是**现成的关联条件。平台只确认了本表这一列 → 对面 `to_column` 这一对；其余键列在本表对应哪一列，平台不知道。**不要按同名列去配**：分区表的主键常被迫带上时间列（如 `(id, create_time)`），而本表的 `create_time` 多半是本表自己的时间，照着连会把几乎所有行静默连丢。能不能只按这一对连，先查对面的 `COUNT(*)` 和 `COUNT(DISTINCT to_column)`：相等说明那一列实际一行一个，只按这一对连就对；不相等就先向用户确认其余键列在本表对应哪一列，确认不了就不要用 |
| 单列 + `verified: WEAK` | 先查清本表有没有类型列、对面是不是复合键；查清了带着完整条件再核对。查不清就不要用，如实告诉用户这条关联不可靠 |

用了这里的关系，答案里写明加了什么条件，例如「（该结论依赖 t_comment.resource_id → t_order.id，join 时限定了 resource_type = 'order'）」。

### ★ 一对多的关联：直接 join 会把金额算大，而且不报错

`joins`（以及 `unreliable_relations`）里另有两样东西专治这件事：`cardinality`（实测基数，`1:1` / `N:1` / `1:N` / `N:N`）和 `auto_joinable`（右侧那一列是不是唯一的）。右侧不唯一时，返回里会多出一条 `fanout_warning`。

**这和关系成不成立是两码事。**一条 `CONFIRMED` 的 `1:N` 关系照样会让你的数算错：左表一行匹配到右表多行，join 之后行数被放大，`SUM` 出来的金额跟着变大——**SQL 不报错，数量级也像那么回事，没人会发现**。

所以：

- 要聚合时，**先在「多」的那一侧按连接键聚合，再拿聚合结果去 join**；
- `N:N` 只当线索，不要直接 join；确实要连就先在一侧去重；
- 没有 `auto_joinable` 这一栏，说明右侧唯不唯一**没人测过**——别默认它唯一，用 `COUNT` 对一下 join 前后的行数。

### ★ 表的形态（`table_shape`）：键值对表不能整列 SUM

`conn_describe` 顶层可能带 `table_shape`，它决定这张表该怎么聚合：

| `table_shape` | 一行是什么 |
|---|---|
| `DETAIL` | 一条明细记录 |
| `MULTI_METRIC_PERIOD` | 一个周期（一天、一个月…）已经汇总好的几项指标 |
| `KEY_VALUE` | **一个指标**：一列放指标名，一列放值 |
| `OTHER` | 不属于以上三种 |

`table_shape` 出现时一定带着 `table_shape_source`：`MEASURED` 是平台用数据实测过的，`MODEL` 只是看结构推断的。**没有 `table_shape` 不等于这是明细表**，只说明平台对这张表没有可靠的形态判断——该怎么聚合，自己从 `fields` 和几行数据去判断。

**`KEY_VALUE` 最危险。** 值那一列里混着不同指标的值——「订单数」「金额」「退款笔数」挤在同一列。直接对整列 `SUM`，就是把订单数和金额加在一起：**语法正确、不报错，数是错的。** 所以：

- 聚合之前，**先按指标名那一列过滤出一个指标**；要几个指标，就按指标名分组；
- 实测过的会给出 `kv_name_column`（指标名列）和 `kv_value_column`（值列），照着用；
- 没给这两栏，说明没实测、或者记下的列和现在的结构对不上——自己从 `fields` 里认清哪列是名、哪列是值，认不清就先查几行看；
- `MODEL` 的 `KEY_VALUE`，`table_shape_warning` 会说清平台测量的情况：没测过、或者测了没得出结论，都还只是推断；**测过而结果不支持这个推断**，先查几行数据确认真的是一列放指标名、一列放值，是才按上面这样聚合，不是就按普通的表处理；
- 指标名各代表什么，和枚举值一样，拿不准就问，不要猜。

返回里的 `table_shape_warning` 会针对这张表再提醒一次。

`MULTI_METRIC_PERIOD` 也别当明细表用：`COUNT(*)` 数出来的是周期数，不是业务笔数；去重人数、比率、平均值这类指标不能跨周期直接相加。

### 枚举值：给了完整集合才能写死条件

字段上可能带 `value_domain`，那是平台**真的去客户库里查过**的取值集合。**判据只有 `complete` 这一个字段：**

- `complete: true` — `values` 就是这一列在库里的**全部**取值。照着它写条件是安全的。用户说「华东区」而库里存的是「华东」这类事故，就是靠它避免的。
- `complete: false` — **不会有 `values`**，`note` 里写着为什么没有：取值种类太多、这一列压根没去查、疑似个人信息、查询失败、这条连接当前没开放样本值（平台就算记过取值也不给你）……**一律不要假设这一列只有某几个取值。**

**`complete: false` 不等于「这一列没有枚举值」**，它多半是「我们没去查」。把这两件事搞混，你会写出一个语法正确、执行成功、永远返回 0 行的条件，然后告诉用户「没有这类数据」。拿不准就自己跑一条 `SELECT DISTINCT`，或者问用户。

**`values` 里只有取值本身，没有含义，平台也不会去猜。** 看到 `st` 的取值是 `0/1/2/3`，不要自己补一句「0 应该是待支付」——那句话完全合理、完全可能错，而且没有任何办法能发现它错。要用到含义，就问用户。

## ★ 必须亮出过程

回答里**必须同时给出**：

- 你实际执行的查询语句（`conn_query` 的返回里有 `statement` 字段，那是平台实际执行的版本，可能被加了 LIMIT）
- 命中的行数（`row_count`）

只给一个数字，就等于让上面那种口径错误彻底失去被发现的机会。

## ★ `truncated: true` 意味着结果不是全集

### SQL 按什么方言写

数据库连接器目前**只有 MySQL 一种**（另一种连接器是 HTTP，不写 SQL）。所以 `conn_query` / `conn_execute` 里的语句一律按 **MySQL 方言**写：

- 标识符用反引号 `` ` ``，不要用双引号；
- 分页用 `LIMIT n` / `LIMIT n OFFSET m`，不要用 `TOP` 或 `FETCH FIRST`；
- 日期函数用 `DATE_FORMAT` / `DATE_SUB` / `CURDATE()` 这一套，不要用 `TO_CHAR` / `NOW() - INTERVAL` 的 PostgreSQL 写法；
- 字符串拼接用 `CONCAT()`，`||` 在 MySQL 默认配置下是逻辑或，不是拼接。

**具体版本（5.7 / 8.x）平台没有下发给你**，所以不要依赖只有 8.0 才有的特性（窗口函数 `OVER()`、CTE `WITH`）——真要用，先用一条小查询试出来，而不是直接用在给用户的答案里。

平台会强制行数上限和结果大小上限。返回里 `truncated` 为 true 时：

- **不要**基于它下任何结论（「一共有 X 个客户」「最多的是 Y」都可能是错的）
- 应该改写查询：加聚合（`COUNT` / `SUM` / `GROUP BY`）、加过滤条件、缩小时间范围
- 并如实告诉用户结果被截断了

## 零结果 ≠ 没有

查到 0 行时，正确的说法是「未查询到符合条件的记录」，并说明你用的条件；**不要**断言「系统里没有这个数据」。0 行同样可能是查错了表、条件写错了、时间范围不对。

### ★ `empty_table`：这一次，零结果就是「没有」

上面那条说的是**你不知道**表里有没有数据，所以不许断言。而 `empty_table` 是**已经知道**了——
它是这条规则唯一的例外，也是唯一一处你该把「0 行」直接讲给用户听的地方。

`conn_catalog` 的每个 entry 上、`conn_describe` 的**顶层**，都可能出现这两个 key：

```json
{ "empty_table": true, "empty_table_at": "2026-09-20 03:00:12" }
```

它的意思是：**平台在 `empty_table_at` 那一刻真的去客户库里探过一次，这张表里一行数据都没有。**
这是事实，不是推测。所以：

- **选表的时候就避开它。** 判断点在第 2 / 第 3 步，不是等你查完拿到 0 行再回头想。
- **别拿它当维表去过滤或分组。** join 到一张 0 行的表，整个结果会被**静默清空**——
  语句没错、执行成功、不报任何错，只是数字悄悄变成了 0。这正是这个标记要挡住的那次事故。
- **真用到了，就如实说**：「这张表里一行数据都没有，无法据此得出结论」。
  **不要**把它说成「本期没有发生」「该客户没有订单」——那是把一个数据缺口讲成了业务结论。
- **不要换个写法反复重试。** 空表上换几种写法，拿到的只是同一个 0 行，
  代价是几次白白打在客户生产库上的查询。
- **结构齐全不代表里面有数据。** `conn_describe` 照样会给出完整的列名、类型、注释、
  甚至关联关系——那些都是结构，与「有没有行」是两件事。

**★ 没有这个标记，不等于表里有数据。** 标记只在平台**确认探到空**时才出现。没有它可能是：
平台探测失败（没权限、超时、表刚被删）、这条连接的出库档位不允许探、或者这张表不在快照里。
所以**不要**把「没有 `empty_table`」读成「平台确认这张表有数据」——平台从没说过这句话。

**★ 观测时刻之后可能已经变了。** 空表被灌进数据是常事。`empty_table_at` 是上一次结构刷新的时刻，
不是此刻。**你自己查到了行，就以你查到的为准**，不要因为有这个标记而否认自己刚查到的数据。

## ★ 写操作（`conn_execute`）

### 1. 默认不开放

**大多数连接只有查询权限。`conn_list` 返回的 `capabilities` 里没有 `write`，就别试。**

每条连接的写策略默认是「只读」，改成「写需审批」或「写自动」要企业超管亲自动手；平台在接入时还会实际验证账号能不能写。没有 `write` 能力时 `conn_execute` 会被直接拒绝——这不是 bug，不要换个写法再试，也不要退回去用 `conn_query` 硬塞一条 UPDATE（那条路同样会被拒）。

建表、改表、`TRUNCATE`、`REPLACE`、存储过程调用**在任何档位都不开放**。`conn_invoke` 的可用 HTTP 方法由管理员在连接上显式配置，默认只有 `GET`。

### 2. 先查后改，每次都要

1. 用 `conn_query` 把**将要被影响的那些行**查出来——把 UPDATE / DELETE 的 `WHERE` 原样搬进 `SELECT`
2. 把**行数**和**几条样例内容**告诉用户
3. 等用户明确确认
4. 才 `conn_execute`

**这一步不是客套。** 查询写错 `WHERE` 只是返回一个错数字，写操作写错 `WHERE` 是**改错客户的生产数据**——不可撤销，而且往往很久之后才被发现。多花一轮确认的成本，和改错一批订单的成本不在一个量级。

### 3. 不要自己决定批量范围

「把所有超期订单改成已取消」「把这批工单都关掉」这类请求里，**「所有」「这批」究竟是多少条，只有查过才知道**。先查出条数和样例给用户看，让用户确认范围，而不是直接推一条 UPDATE 过去。

同样地：不要自作主张放宽条件（「顺手把相似的也一起改了」），也不要为了绕开行数上限而删掉限制条件。

### 4. `pending_approval` = **还没执行**

连接的写策略是「写需审批」时，你的操作会进待审批队列，返回里带 `pending_approval: true` 和 `approval_id`。**此时数据一行都没改。**

必须如实说「**已提交，等管理员确认**」，并把 `approval_id` 给用户。**绝不能**说「已完成」「已修改」——把待审批说成已完成，用户会据此去做下一步动作，而那个前提是假的。

### 5. 超限回滚：转述 + 给方案

平台有单次影响行数上限（返回里的 `max_affected_rows`）。超过时**整条回滚**：返回 `error: forbidden`，`detail` 写明实际会影响多少行、上限是多少。**数据没有被修改**，不是「改了一半」。

这时要：把实际行数和上限如实告诉用户 → 主动提出缩小 `WHERE` 范围分批执行的方案（按时间切片、按 ID 区间、按状态细分）→ 用户确认后逐批执行，每批之间如实汇报进度。

### 6. `affected_rows: 0` 不是成功

0 行通常意味着 `WHERE` 没有命中任何记录。**不要**报告「已完成修改」。回头用 `conn_query` 确认目标数据是否存在、条件是不是写错了，再如实告诉用户。

## 错误怎么读

失败时返回 `{error, title, message, detail}`，`error` 一定是下面十类之一，按它决定下一步：

| error | 你该做什么 |
|---|---|
| `unreachable` / `upstream_error` | 告诉用户目标系统当前不可用，不要重试很多次 |
| `auth_failed` / `forbidden` | 说明权限不足，请用户联系管理员，不要换个写法再试 |
| `guard_blocked` | **按 `detail` 改写语句后重试**。这不是权限问题，**绝不要让用户去联系管理员** |
| `not_found` | 先 `conn_catalog` / `conn_describe` 确认对象名，再重试 |
| `timeout` | 缩小范围（加时间条件、减少返回列、降低 limit）后重试一次 |
| `rate_limited` | 稍后重试，或告诉用户请求过于频繁 |
| `result_too_large` | 加聚合或过滤条件重写查询 |
| `config_error` | 多半是你的入参或语句有问题，按 `detail` 修正 |

**`guard_blocked` 与 `forbidden` 的区别不是「谁拒绝的」，而是你下一步该干什么。**

`guard_blocked` 意味着这条语句/请求**根本没有发到客户系统**，是平台自己的规则在本地拦下的——没带 `WHERE`、一次给了多条语句、用了不开放的语句类型、影响行数超限已回滚。这几种**改写之后就能过**。而 `forbidden` 意味着改写没用，得去找人改授权。

这个区分是被真实事故逼出来的：一条不带 `WHERE` 的 `UPDATE` 被护栏拦下时，早期回给模型的标题是「权限不足」。而「去要更宽的数据库权限」正是整套只读设计要防的那件事——**看到 `guard_blocked` 就改语句，不要把用户推去申请权限**。

## 何时不用

用户的问题与企业业务数据无关（天气、通用知识、写代码、闲聊）时不要调用。**连一次客户的生产库是有成本的**，而且 `conn_list` 返回空时说明这个 Agent 根本没有被授权任何外部系统——此时如实说明，不要猜连接器名字。
