# connector

本技能让你访问企业管理员已经接入平台的外部系统。**平台只提供能力和护栏，不替你决定怎么查——查询语句是你自己写的。**

## 使用顺序

**不要跳步，也不要凭空猜表名。**

1. `conn_list` — 先看有哪些连接器可用、各自有什么能力、健不健康
2. `conn_catalog` — 看某个连接器里有哪些表 / 对象（只给名字和注释，很便宜）
3. `conn_describe` — 看某张表的字段、类型、注释
4. `conn_query` — 写查询语句执行；或 `conn_invoke` — 调接口

前三步都很便宜，第四步才会真的打到客户的生产系统上。**宁可多花两轮确认表结构，也不要写一条基于猜测的查询。**

## ★ 最大的风险：能跑通的查询，不等于口径对的查询

这是本技能里最需要你警惕的事，比语法错误严重得多。

一条 SQL 可以**完全合法、顺利执行、返回一个看起来合理的数字，而口径是错的**。它不会报错，数量级也像那么回事，只有懂业务的人盯着才会发现。典型的歧义：

- 「上个月」含不含本月 1 号？按哪个时区算？
- 「客户」指下单人还是付款方？
- 「销售额」要不要减去退款？含不含税？含不含运费？
- 要不要去重？按订单去重还是按用户去重？

**遇到这类歧义，问用户，不要自己假定。** 一句「这里的销售额是否需要扣除退款？」比一个错误的数字有价值得多。

## ★ 必须亮出过程

回答里**必须同时给出**：

- 你实际执行的查询语句（`conn_query` 的返回里有 `statement` 字段，那是平台实际执行的版本，可能被加了 LIMIT）
- 命中的行数（`row_count`）

只给一个数字，就等于让上面那种口径错误彻底失去被发现的机会。

## ★ `truncated: true` 意味着结果不是全集

平台会强制行数上限和结果大小上限。返回里 `truncated` 为 true 时：

- **不要**基于它下任何结论（「一共有 X 个客户」「最多的是 Y」都可能是错的）
- 应该改写查询：加聚合（`COUNT` / `SUM` / `GROUP BY`）、加过滤条件、缩小时间范围
- 并如实告诉用户结果被截断了

## 零结果 ≠ 没有

查到 0 行时，正确的说法是「未查询到符合条件的记录」，并说明你用的条件；**不要**断言「系统里没有这个数据」。0 行同样可能是查错了表、条件写错了、时间范围不对。

## 只读

这些连接器只被授予了查询权限（平台在接入时实际验证过账号写不了）。不要尝试 `INSERT` / `UPDATE` / `DELETE` / `DROP`，会被直接拒绝。

`conn_invoke` 的可用 HTTP 方法由管理员在连接上显式配置，默认只有 `GET`。

## 错误怎么读

失败时返回 `{error, title, message, detail}`，`error` 一定是下面九类之一，按它决定下一步：

| error | 你该做什么 |
|---|---|
| `unreachable` / `upstream_error` | 告诉用户目标系统当前不可用，不要重试很多次 |
| `auth_failed` / `forbidden` | 说明权限不足，请用户联系管理员，不要换个写法再试 |
| `not_found` | 先 `conn_catalog` / `conn_describe` 确认对象名，再重试 |
| `timeout` | 缩小范围（加时间条件、减少返回列、降低 limit）后重试一次 |
| `rate_limited` | 稍后重试，或告诉用户请求过于频繁 |
| `result_too_large` | 加聚合或过滤条件重写查询 |
| `config_error` | 多半是你的入参或语句有问题，按 `detail` 修正 |

## 何时不用

用户的问题与企业业务数据无关（天气、通用知识、写代码、闲聊）时不要调用。**连一次客户的生产库是有成本的**，而且 `conn_list` 返回空时说明这个 Agent 根本没有被授权任何外部系统——此时如实说明，不要猜连接器名字。
