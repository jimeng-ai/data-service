# data-service v1.1.0 上线说明

> 这份既是 data-service v1.1.0 的上线记录（上线时用 `--notes-file docs/releases/v1.1.0.md` 传给上线脚本），
> 也是这一轮几个仓库一起上线的手册。每次推 main 会自动打版本 tag，但不部署；什么时候上线由你决定（规则见 `scripts/release.mjs` 开头）。

## 这一版包含什么

线上现在是 v1.0.0（2026-09-21 部署的 `f7453d5`）。v1.1.0 带上之后合进 main 的全部改动：

- **数据星图 v2 + v3**：用业务的说法讲清楚一个库的业务对象关系图。语义层补全关系（声明外键、命名规律、整库模型一遍），
  另存一份给人看的业务文字（业务名、一句说明、业务领域、关系角色名），补全链在语义层生成后自动跑、定时对账补跑；
  入口在「数据连接」里每个库的卡片上，和数据连接一样只给企业超管。细节见 `docs/config-changes/2026-10-01-data-graph-v3.md`。
- 角色授权回显不再带已下线的模块码（比如插件），这类角色在 jm-admin 里又能正常保存了。
- **AI 生成 Skill 改为在沙箱里原样跑 skill-creator**（`0286b57`）。细节见 `docs/config-changes/2026-09-27-skill-builder-skill-creator.md`。
- 语义层生成确认的修复（`cfc996c`）。
- 版本号与上线分开：每次推 main 自动打版本 tag，上线改为手动。

后两项的提交在 2026-09-27 就合进了 main，但当时的部署被取消，一直没上线，这次一起发。

## 一、上线前：生产库执行两份 DDL（由你执行，先于一切部署）

两份都是新建表（`CREATE TABLE IF NOT EXISTS`），重复执行无害。必须带 `--default-character-set=utf8mb4`，
否则中文注释会被双重编码成乱码、改不回去。密码用容器里自带的 `MYSQL_ROOT_PASSWORD`，命令里不写明文；库名以生产为准（默认 `data-server`）。

```bash
cd data-service   # 生产机上的仓库目录，先 git pull 到最新的 main
for f in V20260927__skill_builder_session.sql V20261001__data_graph_business_view.sql; do
  docker exec -i ds-mysql sh -c 'exec mysql --default-character-set=utf8mb4 -uroot -p"$MYSQL_ROOT_PASSWORD" data-server' \
    < "modules/data-server/src/main/resources/db/migration/$f" || break
done
```

核对四张表都在（应输出四行）：

```bash
docker exec ds-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N data-server -e "
  SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN (\"skill_builder_session\", \"ai_skill_version\", \"connector_business_view\", \"connector_enrichment_state\");"'
```

| 文件 | 新表 | 漏跑的症状 |
|---|---|---|
| `V20260927__skill_builder_session.sql` | `skill_builder_session`、`ai_skill_version` | 应用照常启动；AI 生成 Skill 的接口全部 500（`Table ... doesn't exist`） |
| `V20261001__data_graph_business_view.sql` | `connector_business_view`、`connector_enrichment_state` | 应用照常启动；数据星图接口 500，补全链每次触发都失败 |

想全面核一遍库结构，用 `docs/RELEASE-CHECKLIST-connector.md` 第 ⑥ 节的自检脚本（容器名换成 `ds-mysql`）。

## 三、上线：一个一个来，等上一个部署成功再上下一个

五个仓库共用一台机器，并发构建会随机失败；上线脚本发现别的仓库有部署在跑会直接拒绝。每一步都在该仓库**干净的 main** 上执行
（先 `git pull --tags`，让本地停在 main 上最新的 tag），脚本会先跑检查，再触发部署、等它跑完，成功后写一条 GitHub Release 当上线记录。
不写版本号就上 main 上最新的 tag；写这份说明时三个仓库最新的都会是 v1.1.0，之后 main 上再有提交就会是更大的版本号，照样上最新的。
也可以不用脚本：GitHub → 该仓库 → Actions → Deploy → Run workflow，在 Use workflow from 里选 tag（这样不跑检查、不写上线记录）。

| 顺序 | 仓库 | 命令 | 说明 |
|---|---|---|---|
| 1 | jm-agent-sandbox | `nvm use 22`<br>`export PATH="$(dirname "$(uv python find 3.12)"):$PATH"`<br>`npm run deploy -- --notes-file docs/releases/v1.1.0.md` | AI 生成 Skill 要靠它的 skill-builder 运行形态。上线前检查里的单测要 Python ≥ 3.10，系统自带的是 3.9，第二行换成 uv 的 3.12。镜像构建约 20 分钟 |
| 2 | data-service | `node scripts/release.mjs deploy --notes-file docs/releases/v1.1.0.md` | 必须在第一节的 DDL 之后。检查是本地 `mvn -o` 安装加 data-server 全量单测 |
| 3 | jm-agent-front | `nvm use 20`<br>`npm run deploy -- --notes-file docs/releases/v1.1.0.md` | 需要 data-service ≥ v1.1.0（数据星图接口的新字段、AI 生成 Skill 的新接口） |

jm-admin、jm-operator 这次不用上：它们的 main 上只多了改上线方式的提交。

**第 1 步可能失败，不影响后面两步。** 沙箱上一次部署（2026-09-27）在「Set up Python for skill-creator tests」这一步失败，
之后的修复（`d9b14e2`）那次运行被取消、没在 runner 上验证过，这次是第一次真跑。失败时部署步骤会被跳过，线上沙箱保持 v1.0.0；
照样可以继续上第 2、3 步——数据星图不依赖沙箱，AI 生成 Skill 会提示「沙箱版本不支持 Skill 构建器」（不会乱跑），沙箱修好再上就恢复。

## 四、上线后核对

1. 网关：`curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:20011/data/actuator/health` 不是 `000`。
2. 前端（10012）用企业超管登录 → 侧栏「数据连接」→ 数据库卡片上点「查看星图」→ 能看到这个库的对象和关联。
   还没整理过的库会挂「业务名称整理中」，这是正常的。
3. 补全链：启动 5 分钟后第一次定时对账，之后每 10 分钟最多给一个连接补跑，N 个连接全部补完约 N × 10 分钟，每个连接调模型约 4–6 次。
   `docker logs ds-data-server 2>&1 | grep 补全链` 能看到「补全链定时对账：派发」和「补全链完成 … 结果=READY」。
4. 权限：成员侧栏没有数据连接，直接打开某个库的星图地址，页面显示「仅企业超管可访问」；jm-admin 的角色授权里没有「数据星图」。
5. 沙箱上线成功的话：AI 生成 Skill 能开会话、跑完一轮。

## 五、回滚

- 某个仓库有问题：GitHub → 该仓库 → Actions → Deploy → Run workflow，在 Use workflow from 里选 `v1.0.0`。新表都是纯新增，回滚代码不用动库。
- 只想停掉数据星图的补全链（比如控制模型费用）：Nacos `data-server.yml` 设 `connector.semantic.enrichment.enabled: false`，
  再重启 data-server（配置类没有标 `@RefreshScope`，以重启为准）。页面照常用已经整理好的数据。
- 前端回滚到 v1.0.0 会连带撤掉 2026-09-27 以来的全部前端改动（工作台改版等），见 jm-agent-front 的 `docs/releases/v1.1.0.md`。
