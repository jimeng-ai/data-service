## 0 勘误表

| # | 上游断言 | 实际 | 后果 |
|---|---|---|---|

| — | 三条审批修复已落地（trace_id / estimateAffectedRows / 多表 UPDATE 拒绝） | **全部属实**，两仓库 HEAD 都在，带单测 | 无需改动 |

另：上游给的 DDL 里 `uk_connector_semantic` **不含 `deleted`**，而本仓库全局 `@TableLogic` 逻辑删除，
不含 `deleted` 的唯一键 + 软删 = 第二次插入同一逻辑行必撞键（`ConnectorSchemaMapper:18-24` 记了已咬过三次）。

### 唯一键还有一个上游没提、但会让整张表建不出来的约束

`uk_connector_semantic` 有 6 列，若名字列按 `varchar(255)` + utf8mb4：

```
tenant_id 64*4=256 + connector_id 8 + scope 16*4=64 + (255*4)*3 = 3388 字节 > InnoDB 上限 3072
```

**实测（mysql:8.0）**：`ERROR 1071 (42000) Specified key was too long; max key length is 3072 bytes`。
整张 `CREATE TABLE` 直接失败。

这个错误的危险之处在于它**不会被任何人发现**：本项目没有 Flyway，DDL 手工执行；
而语义层的设计原则是「没有就静默降级成没有说明书」（不变量 8），
于是建表失败之后所有接口照常工作，只是语义层永远是空的。

落地改成 `object_name` / `field_name` / `term` 各 `varchar(191)`（2620 字节，实测通过）。
191 够用：MySQL 的表名/列名上限本来就是 64 字符。收窄的只是进索引的三列，
`gloss` / `detail_json` 不进索引、不受影响。

> 附带后果：`conn_define_metric` 必须在工具层就校验 `term ≤ 191`，
> 否则超长词条会以一条裸 SQL 错误回到模型面前，而这个工具的错误形状是「客户系统出错」——
> 模型会被支去排查一个它根本没碰过的数据库。

## 1 锚点必须按 scope 分粒度（对 §8 的修正）

上游把 `anchor_hash` 定义成「对应对象的 content_hash」，同时又要求「加一列不改变『这张表是订单主表』」。
这两条在表级锚点下不可能同时成立。落地改成：

| scope | `anchor_kind` | 锚什么 | 什么时候失效 |
|---|---|---|---|
| OBJECT | `NONE` | 不锚结构 | 只有整张表消失（`ObjectDiff` = `REMOVED`） |
| FIELD | `FIELD` | 这一列自己的 `name:type:nullable:comment` | 改这一列。改别的列不影响 |
| JOIN | `JOIN` | 左右两列指纹的组合 | 任一端变了 |
| METRIC | `COLUMN_SET` / `NONE` | 有 `sql_fragment` 时锚它引用的列集合；纯人工口径无 SQL，为 `NONE` | 引用的列变了 |
| CAVEAT | `NONE` | — | 表消失 |

字段指纹与 `ConnectorSchemaService.structureFingerprint` 里每列那一段**刻意同形**，
这样两边对「什么算结构变了」的判断一致。

STALE 必须**可撤销**：结构改回来要能恢复，否则一次误报会永久污染那条语义。

## 2 口径沉淀需要一条写路径（上游空白处）

§7「不加新工具」说的是**读**。把用户澄清的口径落库需要写入口，上游没有定义它。

在对话里嗅探「用户刚刚回答了一个口径问题」恰恰是交给模型理解。工具调用是确定性的。

现状确认：`skills/connector/SKILL.md:33` 已经写着「遇到这类歧义，问用户，不要自己假定」——
上游说的「模型现在本来就在问，缺的是记住」属实。所以改动确实只有「记住」这一步。

## 3 `create_user` 会是 null，而 §5 要求「记住是谁答的」

口径在**对话流**里沉淀，对话跑在 `streamExecutor` 上，经 `MdcAsyncSupport.wrap`——
它只传 `TenantContext` 和 MDC，**不传 `RequestContextHolder`**（`MdcAsyncSupport:28-30`），
于是 `MyMetaObjectHandler.getCurrentUserId()` 返回 null，`create_user` 填不上。
`ConnectorHealthJob:51-52` 已经记过同样的现象。

所以 `answered_by` / `answered_name` / `answered_at` 是**独立业务列**，不复用审计字段。
`answered_name` 存**快照**而不实时 join：人离职改名后，「9 月 13 日由张三确认」应该还是张三。

## 4 变更留痕现在就做（与 §5 的分歧）

上游把它推给「将来若发现口径被改坏得太频繁，最小的补救是记录每次变更」。**不采纳这个时序。**

连「什么时候开始错的」都查不出来。而且 `BaseEntity` 已经免费给了 who/when，

记录变更 ≠ 重新引入审核。上游把这两件事混为一谈了：审核是**事前**拦截，留痕是**事后**取证。
零人工审核这个约束反对的是前者，不反对后者。

## 5.5 实现期发现、且推翻了上游描述的两件事

### 接入即触发原本是死的

上游 §8 写「接入时（异步，一次）S0→S4」，读起来 S0 结构快照是推导的一部分。实现后实测：
`ConnectorService.create()` 只插 `connection` 行，**全仓库唯一写 `connector_schema` 的地方**是
`ConnectorSchemaService.refresh()`，而它唯一的调用方是管理台的手动端点。
于是建连之后派发的推导每次都读到空快照，`semantic_status` 一律写成 FAILED——
每条新连接都显示「语义层：失败」，一行说明书都产不出来，而这正是 P1 的主打卖点。

落地改成：后台任务在快照为空时**自己补拉一次** `refresh()`，补完仍空才算失败。
同时保住「推导只读快照、零客户侧访问」这条不变量——去打客户库的是 bootstrap 那一次补拉，不是推导本身。
另外 HTTP 连接器没有 DESCRIBE 能力，`refresh()` 对它必然抛异常；那不是故障，
所以单独给它一个 `NOT_APPLICABLE` 终态，而不是在一条健康的连接上画红字。
**一个会喊狼来了的状态字段，很快就没人看了。**

### 认领凭据不能借用 `semantic_synced_at`

为了让「进程中途重启后卡死的 RUNNING 还能被抢占」，认领必须自带时间戳。
最初借用了 `semantic_synced_at`，代价是 RUNNING 期间那一列的含义变成「本次开始时间」。
**这个代价比看上去大**：`writeStatus` 在失败时也盖戳，于是一次失败的重试会把
「上次什么时候还是好的」直接抹掉——而那恰恰是排查时唯一有用的信息。

因为这份 migration 还没上线，加一列是免费的，所以拆成两列：
`semantic_claim_at` 是机器用的并发凭据（CAS + 超时抢占），
`semantic_synced_at` **只在成功时盖戳**。成本不对称是这里的判据：现在加一列是几十行，
上线之后每个环境都要手工执行 DDL。

## 5.6 P1 收尾：三块补齐

| 件 | 做法 | 要点 |
|---|---|---|
| 默认注入目录（`P1-SCHEMA-OVERVIEW-INJECT`） | 新增 `ConnectorOverviewService`，挂在 `SkillRuntimeService.applySkillContext` 上（与 `resolveRagSkillVisibility` 同构） | 只读**我们自己的快照**，不打客户库；必须做列投影——该方法**每个请求都跑**，而 `connector_schema` 每行带 longtext `detail_json`，不投影就是每轮对话拖几 MB |
| 前置缺口②：按重要性截断 | `ORDER BY` 改成按 `LENGTH(TABLE_ROWS)`（十进制位数 = 数量级）降序，`TABLE_NAME` 兜底 | 用位数而不是 `FLOOR(LOG10())`：后者走浮点，`LOG10(1000)` 在某些平台得 2.9999… 会 FLOOR 成 2，让 SQL 侧和 Java 侧在 10 的整数次幂上分叉。按**数量级**分档还顺带解决了确定性——行数估算在 1000↔1050 抖动不会改变去留，否则漂移检测会永远报 churn |
| 管理台界面 | `ConnectorSemanticDrawer` + 列表页状态列 + 「重新生成」 | `source=HUMAN` 必须与机器推断视觉上分开：平台刻意不提供口径编辑入口，这个界面是**唯一**能让人发现口径记错的地方 |

### 排序一改，两处文案就跟着失真——都得同步改

这两处很容易漏，因为它们不在被改的文件里：

1. **`conn_catalog` 给模型的截断警告**。从字母序改成按重要性之后，「只有 200/500」的含义变了：
   从前是「名字排在后面」，现在是「这张表很小」。而字典表、配置表这类 join 绕不开的东西恰恰都很小。
   模型知道漏掉的是小表，才会想到直接按名字 `conn_describe` 去问；以为漏掉的是「z 开头的」，它只会去猜名字。
2. **`SKILL.md` 的「使用顺序」**。它原本写着「不要跳步」并要求第 2 步必调 `conn_catalog`。
   默认注入了概览却不改这一句，**那一次往返一次也省不下来**，① 的价值完全落空。
   改成条件分流：概览命中可直接进第 3 步；找不到 / 概览自称只列了一部分 / 怀疑结构变过——三种情况必须回查。

> 教训：技能文档里**不要逐字引用另一处代码的字符串**。第一版这里引了「仅列出 N 张」，
> 而代码里实际写的是「只列出」；描述条件而不是复制原文。

## 5.7 P2/P3/P4：三处刻意偏离文档字面参数

文档 §3 给的 S3 调优值是抄 Tursio 的。实现时有三处按第一性原理推翻了字面写法，理由都写进了代码注释，
**这里再记一遍是因为它们看起来像「没照着做」，最容易被下一个人改回去**。

### ① 包含率按「去重取值」算，不按行算

按行算两个方向都会被热点键带偏：
- 99% 的行填同一个合法外键时，剩下 1% 全是脏值也能算出 99% —— **假阳性**；
- 反过来，一个占了 99% 行的历史脏值（比如遗留的 `0`）会把一条完全正确的关系压到 1% —— **假阴性**。

去重后一个取值一票，这也正是 inclusion dependency 的标准定义。
所以依据文案是「采样 1000 个**取值**，命中 970」，不是文档原文的「采样 1000 **行**」。

### ② 不对包含率样本做 IQR 截尾

文档写「采样前清洗：去 NULL / 空串 / **数值取 IQR 内**」。前两项照做，第三项反了：

IQR 截尾是**采集列统计量**时的清洗（不让离群值带偏 min/max/均值）。用在包含率样本上方向相反——
**悬空外键恰恰住在分布尾部**（被清理过的历史 id、迁移越界值），截掉尾部会让包含率虚高、制造假阳性，
与 S3「P 优先于 R」的取向正好相反。

> 附带发现：空串过滤**只能加在字符型列上**。在数值列上写 `x <> ''`，MySQL 会把 `''` 隐式转成 `0`，
> 把 `0` 这个合法取值整批剔掉——不报错，只让包含率莫名其妙。

### ③ 10⁶ 采样预算做成「本轮总采样行数」，不做成 SQL 里的 LIMIT

写进内层派生表会阻止 derived table merge、让 MySQL 物化一张百万行临时表，比它想省下的扫描更贵。
改成跑完一条累加一条、用尽即停，剩余候选如实标「没轮到」。

### 另外：「没查」和「查了判不出来」必须是两个值

`V_NONE` = 没查（档位不允许 / 预算用尽 / 被中止 / 开关关闭）；
`V_UNDECIDABLE` = 查了但判不出来（样本 < 10 / 超时 / 权限不足）。
注入层对这两者说的是**不同的话**，用错等于凭空声称做过一次不存在的验证。

且 **没有任何一条分支会把超时翻成 `REJECTED`**——用一次慢查询静默删掉一条正确的关系，
是这套验证机制能犯的最坏的错。

## 5.8 采样验证与值域剖析必须是推导之后的独立异步阶段

S3 自节流 30 次/分钟、S4 20 列/分钟，200 条候选最坏 ~20 分钟，值域 ~30 分钟。两条硬约束：

1. **不能内联进 derive**。`semantic_status=RUNNING` 挂半小时会让管理台看起来像卡死，
   而且挡住 claim/CAS 的重试窗口。derive 照常先写 READY（说明书本来就已可用，关系只是标着「未经数据验证」），
   验证阶段随后异步跑、逐条回写。
2. **不能挂在 `streamExecutor` 上**。那个池是 `queueCapacity=0 + CallerRunsPolicy`——池满时任务
   **就地跑在调用线程上**，等于把半小时加到一次建连请求上。必须单开带队列的池。

### 平台侧限流预算是一本要一起看的账

网关的 platform 桶默认 60 次/分钟，S3 自节流 30、S4 自节流 20，合计 50。
**再加第三条平台侧剖析路径就会越过 60**，表现是某一路被 `RATE_LIMITED` 中止。
新增平台剖析路径时这三个数必须一起算。

## 5.9 接线期的几处判断

**S1 的关系不能被当外键信任，也不能被 S3 信任。** 视图里的等值条件不一定是主外键关系——
`a.status = b.status` 也是合法等值 join。所以语料关系 confidence 封顶 85、`verified=V_NONE`，
并且应当**被 S3 复核**而不是被它当作已知事实。

**语料行不做 mirrored（不在右表那头也挂一份）。** JOIN 行的唯一键里只有左侧列，
镜像行会挂到右表的主键列上，而主键列通常被多张表引用——镜像必然系统性撞键、只活下来一条，
还会把模型推的真行挤掉，同时让 S3 的候选数（也就是客户侧成本）翻倍。

**撞键时语料压过模型，不比 confidence。** 模型的 confidence 是「我有多大把握」，
语料的是「在几处见过」，两个不同量纲的数比大小，会让一条人真写过的关系被一条名字像的猜测挤掉。
判据回到那条总原则：**有没有外部依据**。

**`V_NONE`（没探查）的结论一个字都不写回去。** 写了会用一句泛泛的「未经数据验证」
覆盖掉 S1 留下的来源线索——等于「这一轮什么都没做，却顺手删掉了唯一的线索」。
跳过还保证下一轮（档位调高后）它仍然是候选。

**来源单独存一个 `source_sql` 键，不靠字符串手术从 `basis` 里保。** S3 的 `detailPatch()`
必然覆盖 `basis`，任何「拼接式保留」迟早会在某次措辞变化时静默失效。

**审计动作名必须分开。** S4 读的是真实取值（第 3 档），S3 只读聚合数（第 2 档），
敏感度差一个量级。客户 DBA 在 `connector_audit` 里最常做的就是按 operation 过滤——
分名之后他不必读语句原文就能回答「平台到底有没有读过我的业务数据值」。
合成一个名字，这个问题就只能靠逐条看 SQL 回答，而那正是审计表存在的意义。

## 5.10 第 3 档的开关必须有界面，否则两头都错

后端把「留空 = 默认档，**不是**保持原样」定得很对，理由是两种错的代价不对称：
降档错了表现为推断变差、有人来问——吵闹、能被发现；留档错了表现为真实取值继续出库
而谁都没有再决定过一次——安静、发现不了。

但这条规则有一个前提：**编辑表单必须把当前档位回填再提交**。前端不知道这个字段时，
后果有两个，第二个更糟：

1. 第 3 档没有任何开启入口 → 值域剖析永远跑不起来；
2. 任何一次编辑（哪怕只是改个显示名）都会把已开的第 3 档**静默降回第 2 档**。

界面上还必须**同时说清两头的代价**。只讲第 3 档的风险、不讲第 1 档的代价，
会把所有人推到最严档，然后这个功能在没人知道为什么的情况下悄悄失效
（纯元数据档上真实生产库的 join 推断精确率约 0.49）。

## 5.11 第二、三轮（2026-09-15）：补齐剩余缺口时的关键判断

这两轮补的是 §8 周期刷新、ADDED 增量、table_shape、WEAK/多态外键/复合键、REMOVED 管理台影响条数，
以及三轮对抗审查查出的问题。下面只记**以后最容易被人改回去**的判断。

### 刷新与漂移

- **健康探测（ping）和建连/测试时的 probe 不走网关，是有记录的例外。** ping 是 `SELECT 1`：走网关会让每条连接每天往
  `connector_audit` 灌约 288 行，恰好伤害「DBA 按 operation 过滤」这个审计的核心用途；还会和采样验证抢每实例 permit，
  抢不到时一条忙碌但健康的连接会被误判 DOWN。probe 发生在连接尚未落库（dryRun 用负数合成 id）时，网关要求落库行，用不了。
- **定时刷新以快照年龄为时钟，不用进程内定时器。** push main 即部署，进程内 6 小时定时器在部署勤的时候一次都不会触发。
- **快照里「不在」有四种含义，只有一种算删表。** 描述到的（DESCRIBED）、目录列出但超出 200 张描述上限的（LISTED_ONLY）、
  目录完整且确实不在的（ABSENT）、目录本身被截断而拿不准的（UNKNOWN，再按名字精确查一次 information_schema 解开）。
  只有 ABSENT 产生 REMOVED 和 STALE。否则一张只是行数跨档被挤出前 200 的表，会被当成消失，挂在上面的口径停止注入，
  管理台还会叫业务方重答口径。
- **空目录不落库；更旧的拉取不覆盖更新的快照。** 客户库从 N 张表突然变 0 张，远比「真的删光了」更可能是恢复、迁移或收回授权；
  一次先开始的长拉取晚于一次短拉取提交，会把刚标 STALE 的行复活。两者都拒绝落库并在结果里说明。
- **待处理的删除要持久化（Redis 30 天）。** 快照已提交而漂移处置失败时，下一次刷新靠它补报影响；也靠它区分
  「这次真的消失」和「上线前早已消失、被旧代码复活成 DRAFT 的表」，避免上线后第一次刷新把早已消失的表误报为本次消失。
- **漂移回写只写变化的列，并带乐观条件。** 整行 updateById 会在定时刷新与用户在对话里确认口径同时发生时，
  静默冲掉人刚答的口径和它的留痕。

### 关系

- **REJECTED 永不注入；WEAK、多态外键、复合键移出 joins，放进 unreliable_relations，带 care_reason 与 condition。**
  包含率 0.5–0.9 的常见成因正是多态外键或复合键，按单列 join 不是「部分正确」，而是连进看起来合理的错误行，
  拿 COUNT 对 join 前后行数也核不出来。
- **多态外键的判别值是第 3 档真实取值**（连 GROUP BY 判别列都会让取值离开客户库），第 2 档只做结构标注。
  **自增主键的库上分组包含率无法区分类型**：本地实测 `role_resource` 上 AGENT 组与 KB 组对 `agent.id` 的包含率都是 100%，
  只能靠「判别值与表名对应」打破平局，对应不上就判不确定。判别列为 NULL/空的行必须纳入分组，否则会凭部分证据判 REJECTED。
  列名前缀本身就能解析成目标表时（`user_type` + `user_id` → `user`），按普通外键处理，避免误报。
- **复合键只确认 from_column → to_column 这一对，不按同名列推其余键列。** 分区表主键被迫带时间列（本地实测
  `orders_p PRIMARY KEY(id, create_time)`），按同名列连会把几乎所有明细连丢。含可空列的唯一键要额外告警。
  **注入条件、care_reason、SKILL.md、tools.json 四处必须说同一句话**——曾经只改了前三处，工具描述仍在推模型连全部键列。
- **增量推导的 upsert 不毁证据。** 表重新出现时模型会重提同一关系：结构未变的已验证结论（含 REJECTED）必须保留，
  S1 语料关系不被更弱的模型猜测覆盖，已实测的表形态保留。
- **结构补标只在目标表唯一键已知时写 SIMPLE**；未知就不写，留给以后再判，否则「不知道」会被冻结成永久 SIMPLE。

### 目录排序

- 外键被引用数作为同一数量级内的次级排序键。**多数客户库声明 0 个外键，对它们无效**，这一点写在代码注释里。
- **可用性优先于排序稳定。** MySQL 5.x 没有事务性数据字典，加一次 KEY_COLUMN_USAGE 聚合耗时约翻倍，大库会超过 15 秒超时，
  所以 5.x 确定性地走兜底排序；8.0 上主 SQL 偶发超时时，本次请求用兜底回答而不是报错，代价是那一次刷新保留的 200 张可能不同。

### 第 3 档与形态

- **真实取值永远不写进自由文本说明**，只放在受档位管控的 value_domain / discriminator_value 里；降档时清除已存的取值。
- **「这一行是不是值域采集行」只有一个判定方法，写入侧与注入侧共用。** 两侧曾各写一份且宽窄不一：清除逻辑判得宽，
  会在默认档连接的每次刷新里把模型写的真实字段含义覆盖成一句假话，而注入层判得窄、不拦，于是把这句假话发给模型。
- table_shape 只认四个枚举值，旧版推导写的自由文本（主表/明细表/…）不映射——旧词表里的「其他」会被映射成 OTHER，
  而 OTHER 等于断言「不是键值对表」，会压掉聚合告警。键值对表实测属于派生统计（第 2 档），放在验证阶段做，推导本身仍对客户库零访问。
- **增量覆盖以数据判断，不靠进程内队列。** 每次刷新都按「快照里有、却没有表用途行」补写，Redis 冷却防止对模型永远写不出东西的表无限重试；
  进程内队列扛不住 push 即部署。

## 6 已知代价，不掩饰

- **HTTP 连接器拿不到任何语义层。** 见勘误 2。
- **口径无权限区分。** 任何能对话的人都能覆盖口径，一个不懂业务的人可以把对的改错。
  唯一的发现途径是模型引用时「亮出依据」——所以那不是好习惯，是**唯一的纠错通道**。
- **审批人和模型共用同一个错误来源。** 要判断一条 UPDATE 对不对，人必须知道「这张表一行是什么」，
  而他唯一能查的就是这份语义层，正是可能误导模型的那一份。审批不构成独立校验。这是结构性代价。
- **第一个被问到口径的人不知道自己在为全公司定义它。** 上游说「他本来就要答这一句」——
  不准确：本来那一句是「这次这么算」，沉淀之后变成「以后都这么算」，责任重量不同。
  缓解是沉淀时明说一句「我记下了，以后默认这么算」，成本一行字。

## 7 推送时仍未解决的问题（2026-09-15）

第三轮对抗审查提出的问题里，下面这些**在默认配置下不损害生产**，按用户要求先随本次推送上线，再单独处理。
凡是相对线上版本的回归，都已在推送前修掉（见 5.11「第 3 档与形态」「目录排序」、以及 tools.json 的复合键描述）。

| 范围 | 问题 | 后果 |
|---|---|---|
| 第 3 档 | 判别列为 NULL/空的分组命中不足 9 个时仍可能判 REJECTED | 一条真实的多态外键被静默挤出注入 |
| 第 3 档 | 已确认某判别值、但 NULL 类历史行也指向目标表时，condition 只写等于该值 | 模型漏掉 NULL 类历史行，少算 |
| 降档 | 清除取值时对「多态外键 + 复合键」的 care_reason 用子串匹配整句替换 | 复合键提醒丢失，一行连出多行 |
| 部署 | 生产部署用 `docker rm -f`（SIGKILL），@PreDestroy 里的放锁不会执行 | 每次部署后最长约 30 分钟定时刷新空窗，仅 debug 日志 |
| 结构 | 已判 SIMPLE 的关系，目标表唯一键之后改为复合键不会重查（结构指纹不含索引） | 复合键按单列连，SUM 被放大 |
| 增量 | 部署杀掉增量补写后，若心跳里没有可推导的表，状态不会被接管 | 管理台一直显示「生成中」 |
| 漂移 | 本轮出现并发写跳过时，整份待删名单保留 | 下次刷新可能重新标过期一条刚被人重新确认的口径 |
| 目录 | 兜底的「方言错误」判定是排除式名单且只记在进程内 | 偶发的非超时服务端错误仍可能跨部署切换排序、引起一次漂移 |
| 刷新 | `synced_at` 是秒级 DATETIME，四舍五入可能让「更新快照保护」误拒一次稍晚开始的拉取 | 那一次刷新不落库，下次恢复 |
| 限流 | 定时刷新首次繁忙尝试不限次数，会消耗租户平台令牌 | 可能中断同租户其它连接正在进行的采样验证 |
| 管理台 | 降档后仍把注入层实际不提供的 care_reason、值域说明显示为「模型读到的」 | 管理员对模型所知判断有误（不影响模型） |
| 管理台 | 两次刷新重叠时，REMOVED 表的影响可能被另一次刷新先归属 | 这一次显示「无说明受影响」 |
| 技能文档 | SKILL.md 与 tools.json 描述「没有记下判别值的多态外键」时，缺少「可能只是分类列、此时不应加条件」这层保留意见 | 与注入的 condition 略有出入；两处都要求照 condition 做，以 condition 为准 |

**未验证的环境**：所有新 SQL 只在本地 MySQL 8.0.46 上实跑过；MySQL 5.7、Doris、StarRocks 均未实跑。
